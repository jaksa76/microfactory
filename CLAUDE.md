# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.


## Status

This project is a Claude Code **skills plugin** — pure markdown, no scripts. The previous bash + Docker implementation lives in `legacy/bash-factory/` (with its bats test suite) and the original hub-based design in `legacy/hub/`; both are reference only.

See `docs/ARCHITECTURE.md` for the full design.


## Repository layout

```
.claude-plugin/plugin.json   plugin manifest
skills/
  init-factory/    interview → .microfactory/config.yaml, backend auth, start /loop
  start/           start the implementation /loop at the configured interval
  start-planning/  start the planning /loop at the configured interval
  install-agentize/ install the agentize plugin (agent-readiness skills)
  find-design-improvements/  read-only analysis: candidate refactorings and architecture fixes
  find-testing-improvements/ read-only analysis: coverage gaps, pyramid shape, flaky/slow tests
  find-library-improvements/ read-only analysis: vulnerable, stale, redundant dependencies
  find-ui-improvements/      read-only analysis: runs the UI, reports flow/state/a11y findings
  fill-backlog/    run the finders, merge findings, create approved ones as tasks
  refine-story/    sharpen a vague item via closed proposal-shaped questions (interactive)
  jira-tasks/      Jira backend operations (acli; bundles acli-reference.md)
  github-tasks/    GitHub Issues backend operations (gh; statuses as labels)
  todo-tasks/      local TODO.md backend operations (checkbox states)
  plan-next/       one planning iteration (/loop target)
  implement-next/  one implementation iteration (/loop target)

plans/             plan files generated by plan-next
legacy/            previous implementations (reference only)
```


## Conventions

- Skills are instructions, not code: they describe *what* to do and name example commands; the executing agent adapts them to the user's OS/shell. Don't encode brittle one-liners that only work in bash.
- No secrets anywhere: backend credentials live in `acli`/`gh` native auth; `.microfactory/config.yaml` holds settings only.
- The task backend is the single source of truth. All cross-session coordination goes through issue state (assignee, status/labels/checkboxes) — never through local files.
- The claim protocol (assign → wait → verify → retry) is what makes concurrent sessions safe. Any change to a backend skill must preserve it.
- Workflow skills (`plan-next`, `implement-next`) stay backend-agnostic: they delegate all task operations to the backend skills.
- Keep frontmatter `description` fields precise — they are how the model decides to load a skill.

## Testing

There is no automated test suite for the skills. To verify changes:

- **Todo backend end-to-end** (no external services): create a scratch git repo with a `TODO.md` and a `.microfactory/config.yaml` (`backend: todo`), then run `claude -p "/microfactory:implement-next"` headless and check the checkbox flips, the note line, and the commit. Same idea for `plan-next` with a `[needs-plan]` item.
- **Live smoke**: one issue in a test Jira project or scratch GitHub repo through `/plan-next` → approve → `/implement-next`.

The legacy bash implementation keeps its bats tests under `legacy/bash-factory/` (see `docs/acli.md` when interacting with Jira there).


## Code style

Implement the simplest solution that could possibly work.
Refactor aggressively.
Keep responsibilities well defined: one skill, one job.
