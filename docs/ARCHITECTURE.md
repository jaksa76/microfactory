# Architecture

## Overview

The factory is a Claude Code **skills plugin**: pure markdown instructions, no bundled scripts, no containers. Each skill describes *what* to do; the agent derives the concrete commands for the user's environment (Windows/macOS/Linux, whatever shell is present).

Worker-based pull model: sessions poll a task-manager backend for eligible work, claim an issue, do the work in the current checkout, push, and update the issue. The task backend (Jira by default) is the single source of truth — there is no local task store and no coordinator process.

```
[Task backend: jira | github | todo]
   <- single source of truth for issue state
   ^v sessions claim, comment, transition
[Claude Code sessions running /loop plan-next | implement-next]
   v  push code and plans
[Git]
```

## Repository layout

```
.claude-plugin/plugin.json   plugin manifest
skills/
  init-factory/    interview -> .microfactory/config.yaml, backend auth, start /loop
  start/           start the implementation /loop at the configured interval
  start-planning/  start the planning /loop at the configured interval
  install-agentize/ install the agentize plugin (agent-readiness skills)
  find-design-improvements/  read-only analysis: candidate refactorings and architecture fixes
  find-testing-improvements/ read-only analysis: coverage gaps, pyramid shape, flaky/slow tests
  find-library-improvements/ read-only analysis: vulnerable, stale, redundant dependencies
  jira-tasks/      Jira backend operations (via acli; bundles acli-reference.md)
  github-tasks/    GitHub Issues backend operations (via gh; statuses mapped to labels)
  todo-tasks/      local TODO.md backend operations (checkbox states)
  plan-next/       one planning iteration (a /loop target)
  implement-next/  one implementation iteration (a /loop target)

plans/             plan files generated by plan-next
legacy/bash-factory/  previous bash + Docker implementation (reference only)
legacy/hub/           original hub-based implementation (reference only)
```

## Configuration

`.microfactory/config.yaml` in the target project, written by `init-factory`. Settings only — **no secrets**; credentials live in the backend CLIs' own auth stores (`acli jira auth login`, `gh auth login`) and the user's git credentials.

```yaml
backend: jira              # jira | github | todo
project: MYPROJ            # Jira key | owner/repo | path to TODO.md
plan_by_default: false     # require an approved plan for all issues
feature_branches: false    # implement on feature/<KEY> branches + PRs
implement_interval: 20m    # /loop interval for implementer sessions
plan_interval: 10m         # /loop interval for planner sessions
jira_site: ...             # jira only
jira_account_id: ...       # jira only
github_username: ...       # github only
```

## Backend skills

Each backend skill documents the same operations for `plan-next`/`implement-next`: find eligible issues, claim, view, comment, transition.

### Claim semantics

Claiming uses optimistic locking so any number of concurrent sessions is safe:

1. Search for eligible unassigned work (oldest/highest-rank first)
2. Assign the first issue to self
3. Wait (~10s Jira, ~5s GitHub) and re-read the assignee
4. If someone else won the race, retry from step 1
5. Transition status (Planning or In Progress)

The todo backend is single-user and skips verification.

### Eligibility

Controlled by `plan_by_default` plus labels: `needs-plan` forces planning, `skip-plan` skips it (and takes precedence). With `plan_by_default: true`, implementation only picks up **Plan Approved** issues (or `skip-plan` ones).

### Status mapping

Jira uses real workflow statuses. GitHub maps statuses to labels (`in-progress`, `in-planning`, `awaiting-plan-review`, `plan-approved`, `in-review`; Done = close). The todo backend maps them to checkbox characters (`[ ]` open, `[>]` in progress, `[~]` planning, `[?]` awaiting review, `[p]` plan approved, `[x]` done).

## Workflow skills

**implement-next** — one iteration: read config → claim an implementation-eligible issue → optional feature branch (`feature_branches` config or `needs-branch` label; `skip-branch` wins) → follow `plans/<KEY>.md`, writing it first (via `plan-next`'s analysis and plan format) and treating it as approved when it does not exist → implement, test, commit → push → PR + In Review (branch mode) or comment + Done (direct mode). Post-push issue updates are best effort.

Every implemented issue therefore ends up with a plan file. The difference between the two paths is who approves it: a human for plans written by `plan-next`, nobody for plans the implementer writes for itself.

**plan-next** — one iteration: read config → claim a planning-eligible issue → explore → write `plans/<KEY>.md` (Summary / Files to Change / Implementation Steps / Testing / Risks) → commit and push only the plan → comment the plan URL → transition to Awaiting Plan Review. A human approves the plan; implementer sessions pick the issue up from there.

**start** / **start-planning** — read config → `/loop <implement_interval> /microfactory:implement-next` or `/loop <plan_interval> /microfactory:plan-next`. Shortcuts for turning an already-initialized session into an implementer or a planner without re-running `init-factory`.

`plan-next` and `implement-next` both take an optional issue key to work a specific issue, and both end quietly when no work is available — the `/loop` cadence replaces the old polling waits. Planner and implementer sessions are intentionally separate so planning is not blocked on human review.

## Finder skills

`find-design-improvements`, `find-testing-improvements`, `find-library-improvements` (and, as the backlog adds it, the UI/UX finder) are **read-only analysis passes**: they explore the project and report ranked improvement candidates — Title / Area / Problem / Proposed change / Effort / Payoff / Risk — capped at ~10 and each backed by concrete evidence in the repo.

Each finder stays in its own lane and hands neighbouring concerns to its sibling — a testing gap that needs a design seam changed goes to the design finder, not into the testing report.

Finders never edit code and never write to the task backend. A separate skill turns findings into backlog items by loading the finders in its own session and doing the backend writes there, so the backend stays the single source of truth and no findings files are needed on disk.

## Continuous operation and scaling

- One iteration = one skill invocation. `/loop <interval> /microfactory:implement-next` keeps a session working.
- Scale out by opening more sessions (locally, on other machines, or in disposable environments such as the project's devcontainer). The claim protocol makes them safe.
- Monitoring = the issue board. There is no factory daemon to inspect.

## What this drops vs. the bash implementation (`legacy/bash-factory/`)

- No Docker worker images, image builder (`worker-builder`), or container runtimes (local Docker / AWS Fargate) — isolation is delegated to wherever the session runs.
- No credential injection (`agent init`, `import-claude-credentials`) — the session and backend CLIs are already authenticated.
- No multi-agent CLI adapters (copilot/codex workers) — the session is the agent.
- No env-var configuration — a committed config file plus native CLI auth.
- No bats test suite — the skills are prose; the legacy suite still covers the archived scripts.
